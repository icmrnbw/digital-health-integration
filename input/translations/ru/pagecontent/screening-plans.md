# Планы скрининга и приглашения

План пациента использует существующий [UZ Core ServiceRequest](https://dhp.uz/fhir/core/StructureDefinition-uz-core-servicerequest.html) с `intent = plan`, категорией SNOMED CT `310422005` и ровно одним идентификатором программы из `https://dhp.uz/fhir/core/sid/prg/uz/program`. Клинический [ScreeningServiceRequest](StructureDefinition-screening-service-request.html) сохраняет контракт источника МИС.

Приглашение Минздрава содержит ровно одну ссылку `instantiatesCanonical = canonical|version` на [UZ Core PlanDefinition](https://dhp.uz/fhir/core/StructureDefinition-uz-core-plan-definition.html); самостоятельный план МИС не содержит этого поля. Происхождение определяют после распознавания плана по intent, категории и программе, а не по форме URL. Оба вида используют UZ Core ServiceRequest без `meta.source` и `occurrencePeriod`. Контракт приложения требует `subject` на пациента, `authoredOn` и хотя бы одного `performer`. Опциональный клинический код передают в `code.concept`, а не `code.reference`. Клинические результаты сохраняют источник. Напоминание через 365 дней не является периодом плана.

`code` необязателен; если передаётся, клинический код записывают в `code.concept`. Программу находят по идентификатору, а не по клиническому коду. `performer` указывает исполнителя услуги. Маршрутизация программы в DMED или систему ВПЧ определяется отдельным соответствием, независимо от создателя плана.

## Программы и определения

[ValueSet типов программ](https://dhp.uz/fhir/core/ValueSet-screening-program-type-vs.html) включает восемь SNOMED-кодов скрининга и сохранённые коды `screening-code-cs`, в том числе патронажные; он шире девяти опросников DMED. При `$expand` запрашивают переводы: SNOMED из `screening-sct-cs`, локальные коды из `screening-code-cs`. `Identifier.value` равен коду, а `Identifier.system` остаётся пространством `prg`, а не URL клинической кодовой системы.

| Программа | Значение идентификатора | Система |
|---|---|---|
| ИБС | `171223006` | DMED |
| Фертильность | `408961002` | DMED |
| Цереброваскулярный скрининг | `mserv-0007-00003` | DMED |
| Гельминтозы | `171147008` | DMED |
| Сердечно-сосудистый риск | `300007000` | DMED |
| Диабет | `171183004` | DMED |
| Опросник по молочной железе | `mserv-0007-00007` | DMED |
| Онкогематология | `762445000` | DMED |
| Опросник по шейке матки | `mserv-0007-00009` | DMED |
| Молочная железа | `268547008` | ВПЧ |
| Шейка матки | `171149006` | ВПЧ |

Клинические коды опросников DMED по молочной железе и шейке матки остаются SNOMED CT. Локальными являются их **идентификаторы программ**. Совпадение клинических кодов или названий не делает программы одной программой. `breast-cervical-unspecified` сохраняется как классификация результатов, но не допускается в новом плане.

Для определений скрининга используют существующие [UZ Core PlanDefinition](https://dhp.uz/fhir/core/StructureDefinition-uz-core-plan-definition.html) и [UZ Core ActivityDefinition](https://dhp.uz/fhir/core/StructureDefinition-uz-core-activitydefinition.html). Приложение требует канонический URL, неизменяемую версию и тот же идентификатор программы, что у плана пациента. PlanDefinition.useContext[screeningFocus] и ActivityDefinition.useContext содержат SNOMED CT `360156006`. Идентификатор программы дополняет стабильный идентификатор записи; Questionnaire.useContext с code = program остаётся отдельной классификацией области интеграции.

`PlanDefinition.action.definitionCanonical` закрепляет канонический URL и версию ActivityDefinition приглашения. [Пример шаблона приглашения](ActivityDefinition-example-hpv-cervical-invitation-activity.html) использует `kind = ServiceRequest`, `intent = plan`, `profile = UZCoreServiceRequest`. Приложение создаёт одно приглашение на пациента/программу и применимое определение, заполняя пациента, категорию, идентификаторы и точную ссылку на PlanDefinition. Questionnaire/Observation не задают условия завершения в этом шаблоне; МИС использует существующий клинический контракт. DHP не вычисляет завершение по результатам. Правила скрининга проверяет приложение; валидация только по Core не подтверждает весь контракт. Новые профили не вводятся.

## Поиск и повторное использование

```http
GET [base]/ServiceRequest?subject=Patient/{id}&intent=plan&status=draft,active&category=http://snomed.info/sct|310422005&identifier=https://dhp.uz/fhir/core/sid/prg/uz/program|{код}
```

Значения параметров в реальном запросе URL-кодируют. Не распознают планы по категории `20135006`, только по code или legacy-префиксам. `20135006` сохраняется в Core для клинических услуг скрининга/патронажа, а не как категория приглашения.

Для приглашения Минздрава дополнительно сравнивают точную пару `canonical|version` с действующим определением программы. Открытое приглашение предыдущей версии не блокирует новое. Нет подходящего текущего плана — можно создать; один — переиспользовать; несколько — конфликт, а не выбор первого. Поиск `instantiates-canonical` проверяют на конкретном сервере. Текущую версию включают в критерии атомарного создания/уникальности; условное создание только по всем открытым планам ошибочно переиспользует старую версию.

GET, затем безусловный POST не гарантируют уникальность. Нужны поддерживаемое условное создание или серверная уникальность с полной согласованной идентичностью плана. Изменение статуса защищают `If-Match`. При активации сохраняют существующие идентификаторы и признаки происхождения.

## Повторные обследования и статусы

Один план ВПЧ используется для повторных обследований пациента по программе, пока актуальны определение и принадлежность к когорте. Само наступление очередного срока не создаёт новое приглашение. Каждое обследование имеет новые клинические направления и результаты с ссылками на тот же план и непосредственный заказ. Выполнения различают по датам и направлениям; новый идентификатор цикла здесь не вводится.

Статус меняет МИС. ВПЧ активирует приглашение и не завершает его после отдельного обследования. DMED ставит `completed` своему плану после сохранения связанного QuestionnaireResponse. Завершённый план DMED исторический; создание нового плана для последующего опросника не описано в исходном контракте и требует отдельного решения. План другой программы не закрывают.

При выходе из когорты или замене PlanDefinition применимость старого плана заканчивается. **Предложение, требующее согласования:** выход из когорты → `completed`; исключение или замена определения → `revoked`. Новый план связывают со старым через `ServiceRequest.replaces`, исторические `basedOn` сохраняют. Стандартное расширение `request-statusReason` необязательно; при использовании код причины можно брать из [черновой ValueSet причин](ValueSet-screening-plan-closure-reason-vs.html). Соответствие причины и статуса не навязывается профилем.

В FHIR `completed` означает выполнение всех подразумеваемых действий. Выход из когорты при невыполненной работе требует отдельного согласования смысла; следует рассмотреть `revoked`. Предложение не включают в production до решения. Отказ, согласие и исключение различают; отсутствие Consent не означает отказ.

## Результаты, совместимость и релиз

Composition остаётся необязательным совместимым ресурсом: ВПЧ может продолжать его передавать по сохранённому профилю. Статус retired не вводит запрет на валидные исторические payload. Новый процесс не требует Composition и не использует его для завершения плана. Результаты получают по точному идентификатору программы либо через `basedOn` на план. [ScreeningComposition](StructureDefinition-screening-composition.html) получает статус retired, но сохраняется для проверки исторических документов; прежние примеры являются историческими. Эта правка исходников не удаляет и не мигрирует записи на сервере.

Сохраняют ссылки на непосредственный заказ вместе со ссылкой на план: Core Observation `basedOn` 0..*, патоморфологический ServiceRequest 1..*, иммуногистохимический Observation допускает несколько ссылок. Такие payload начинают отправлять после развёртывания совместимого Core на сервере.

Старое пространство `https://dhp.uz/fhir/core/sid/uz/screening-program-type` не используют для новых записей. Историю читают отдельным явным путём миграционной совместимости; legacy-признаки не возвращают в распознавание новых планов и не добавляют как алиасы. Канонический URL NamingSystem сохранён. Клинические направления сохраняют профиль и `meta.source`. Определения используют существующие профили Core; focus и дополнительные правила плана проверяет приложение.

Минздрав согласует границы возрастных когорт, дату оценки и правила включения, цель и правовое основание согласия, срок и область отказа, закрытие и преемственность планов. Общие Group и Consent для обмена данными не становятся автоматически контрактом скрининга. Видимость результатов пациенту — отдельное продуктовое решение.

Core 0.11.0 опубликован без ServiceRequest в ValueSet ActivityDefinition.kind. Сначала выпускают и регистрируют обновлённый Core 0.11.1, затем Integrations с шаблоном приглашения, реестром программ, отдельными программами DMED и изменениями кардинальностей. Оба пакета подключают в `fhir.lock`. Подготовка исходников и локальная проверка не означают выпуск релиза или развёртывание на сервере.

Календари вакцинации ищут через `PlanDefinition?context-type-value=focus$http://snomed.info/sct|33879002`; отсутствие focus не означает вакцинацию. Для регионов используют `states-cs`.
